# LaLea 第一輪低擬真原型邊界與驗證計畫

> 狀態：待執行  
> 最後更新：2026-08-21  
> 階段：正式開發前的互動與內容驗證

## 1. 原型目的

第一輪原型不是縮小版正式產品，也不驗證完整技術架構。它只回答三個核心問題：

1. 使用者能否在零散時間中快速開始並完成一個微型單元？
2. 不使用開放式問答時，選擇、排序、固定句塊與短分支對話是否仍有學習價值？
3. 純聽模式是否值得作為 LaLea 的核心差異功能繼續投入？

若這三點尚未成立，不應先投入帳號、完整資料庫、AI 自動化或大量教材。

## 2. 原型形式

第一輪採可點擊的手機低擬真原型，優先模擬 iPhone 與一般 Android 手機寬度。

建議先用靜態 HTML／互動原型工具或簡單視覺稿呈現，不建立正式 Next.js 應用架構。原型資料全部為固定樣本，不連接 PostgreSQL、不實作登入、不呼叫 AI，也不將結果視為正式學習紀錄。

原型需要能在實際手機瀏覽器開啟，因為滑動距離、按鈕位置、音訊操作與單手使用無法只靠桌面畫面判斷。

## 3. 本輪包含的流程

### 流程 A：零散時間開始學習

```text
首頁
→ 查看下一個建議單元
→ 選擇 1／3／5 分鐘與靜音／可聽
→ 開始單元
→ 完成兩至三題
→ 查看完成回饋
→ 選擇再學一個或先休息
```

### 流程 B：中途離開與續接

```text
進行到第二題
→ 關閉單元
→ 回到首頁
→ 顯示未完成單元
→ 從第一個未完成題目繼續
```

原型只模擬狀態，不需要真正持久化到資料庫。

### 流程 C：純聽模式

```text
首頁切換純聽
→ 開始今日清單
→ 播放／暫停／重播／下一個
→ 標記不熟
→ 查看清單位置
→ 結束播放
```

第一輪驗證前景播放與控制理解度。鎖定畫面背景播放另做獨立技術實驗，不混入低擬真測試。

### 流程 D：快速加入詞彙

```text
詞彙庫
→ 輸入 hold off on
→ 找到既有詞義
→ 確認加入
→ 顯示可開始學習
```

另模擬一次沒有既有詞義的結果，確認「已保存、等待補齊」是否容易理解。

## 4. 必要畫面

第一輪只製作以下畫面與必要狀態：

1. 首頁／今日學習。
2. 單元開始說明。
3. 選擇題。
4. 聽力辨識題。
5. 固定句塊排序題。
6. 作答回饋。
7. 固定分支短對話。
8. 中途離開確認。
9. 未完成單元續接狀態。
10. 單元完成。
11. 純聽播放器。
12. 純聽清單與設定面板。
13. 詞彙庫。
14. 快速加入詞彙。
15. 已找到詞義／等待補齊結果。

設定、完整學習紀錄、登入、操作者工作台和桌面版只需保留入口位置，不製作完整流程。

## 5. 使用的樣本內容

主流程使用第一堂課「請對方說明並確認理解」，因為它同時包含閱讀、聽力、句塊與短對話。

另外兩堂只各抽取一個單元，用來檢查播放器是否能重用：

- 回報進度：`We're on track to ...` 的聽力與句塊題。
- 調整會議：`Could we move it to ...?` 的固定分支對話。

純聽清單混合三堂課的 6–8 個片語，模擬到期複習、困難項目與少量新內容。

## 6. 本輪不包含

- 正式 Next.js 專案。
- PostgreSQL、Drizzle 或 migration。
- 真實帳號與多使用者權限。
- 真實間隔重複演算法。
- Codex／Claude 任務匯出與匯入。
- 開放式文字或語音回答。
- 即時 AI 對練與 AI 評分。
- 語音辨識與發音評分。
- YouTube 片段匯入。
- 正式 TTS 生產流程。
- 大量課程內容。
- 完整品牌視覺與動畫。
- Linux 正式部署。

## 7. 原型資料策略

全部使用固定、可重設的假資料：

- 一位模擬使用者。
- 一條繁體中文輔助至一般商務英語的學習路徑。
- 三堂內容原型。
- 固定的今日進度與六筆到期複習。
- 一個未完成單元狀態。
- 一個已存在與一個待補齊的詞彙案例。

資料結構命名應盡量接近未來正式模型，但本輪不因此建立完整 schema。

## 8. 測試方式

### 第一階段：自行走查

使用者在自己的手機上完成四個核心流程。測試時不要由設計文件引導，僅提供任務：

1. 你現在有三分鐘且可以聽聲音，開始一個合適的單元。
2. 完成一題後離開，再找到剛才的進度。
3. 開始純聽並把其中一個片語標記為不熟。
4. 將 `hold off on` 加入自己的詞彙庫。

### 第二階段：短期實用性試用

若第一階段操作沒有重大問題，再以三堂內容進行 5–7 天試用。此階段可以是簡易功能原型，但仍不需要完整後端。

每天記錄：

- 是否主動打開 LaLea。
- 當時可用時間與環境。
- 完成哪些微型單元。
- 哪些操作造成猶豫或中斷。
- 是否使用純聽模式。
- 隔日能否辨識或回想前一天片語。

## 9. 觀察指標

### 操作效率

- 從首頁到開始第一題的時間。
- 開始前的點擊次數。
- 每題是否需要回頭尋找操作。
- 是否發生排序誤觸或音訊意外播放。
- 中斷後能否自行找到續接入口。

### 學習體驗

- 每個微型單元的實際完成時間。
- 回饋文字是否能一次理解。
- 固定題型是否太像考試或過度簡單。
- 句塊題是否要求真正回想，而非只靠拼圖猜測。
- 字幕是否提供幫助但沒有取代聆聽。

### 純聽價值

- 是否願意在不看螢幕時使用。
- 播放順序、停頓與重複是否自然。
- 是否能在需要時找到「不熟」控制。
- 聽完後是否願意完成一個簡短檢核題。

## 10. 第一輪成功門檻

以下門檻用於決定是否進入正式 MVP 開發，不是產品上線指標：

- 在沒有額外說明下，能於 15 秒內從首頁開始合適的學習單元。
- 完成主要流程時沒有無法繼續的操作阻礙。
- 中斷後能在 10 秒內找到並恢復未完成單元。
- 大部分微型單元能在標示的 1–3 分鐘內完成。
- 選擇、排序及固定分支在手機上不需要大量精細操作。
- 使用者認為至少兩種題型有助於記住或使用片語，而不只是閱讀答案。
- 純聽模式至少在一種真實生活情境中具有明確使用價值。
- 三堂課的內容結構可由同一個播放器框架承載，無需為每堂課另造流程。

若未達門檻，先調整流程或內容，不以增加更多功能解決問題。

## 11. 問題與結果記錄格式

每次測試問題以同一格式記錄：

```text
任務：
裝置／瀏覽器：
所在畫面：
預期行為：
實際行為：
是否阻礙完成：是／否
觀察或原話：
建議變更：
```

問題分級：

- **P0**：無法完成核心任務。
- **P1**：可以完成，但需要猜測、返回或外部說明。
- **P2**：不影響完成，但造成困惑、額外操作或內容負擔。
- **P3**：視覺與文字微調。

正式 MVP 開發前至少解決所有 P0，並對 P1 作出明確處理決策。

## 12. 原型後的決策點

完成測試後再決定：

- 是否正式建立 Next.js + TypeScript 專案。
- 哪些題型進入 MVP，哪些延後。
- 首頁是否保留時間與環境選擇。
- 純聽模式是否列入首版必要功能。
- 是否需要先做 PWA，或維持一般手機網頁。
- 正式資料庫第一批 schema 與事件紀錄範圍。
- 第一批正式教材需要多少內容。

## 13. 建議執行順序

1. 製作灰階手機畫面與可點擊流程。
2. 插入第一堂完整樣本及另外兩堂代表單元。
3. 在桌面瀏覽器完成內部走查。
4. 在 iPhone Safari 與 Android Chrome 實機走查。
5. 修正 P0／P1 操作問題。
6. 進行 5–7 天短期試用。
7. 根據結果決定是否開始正式 MVP 開發。
